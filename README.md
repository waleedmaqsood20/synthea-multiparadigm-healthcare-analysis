# Multi-Paradigm Healthcare Data Analysis Using SQL, MongoDB and PySpark

**Academic Data Analysis Project — Master of Data Science, UniSQ**

## Overview

This project analyses a synthetic Australian healthcare dataset generated
with Synthea, comparing medication utilisation between patients with a
chronic condition and patients without one. Instead of answering that
question once, I implemented it three times over the same 5,000-patient
subset: as relational SQL, as a MongoDB document/aggregation model, and as a
PySpark distributed pipeline, for three separate parts of the same
assignment sequence. The interesting part isn't the three technologies on
their own, but whether the same result holds up when the same data is
modelled and queried in three structurally different ways — and what it
takes to reconcile them when they don't agree by default. This repository
contains the data-preparation script, all three implementations, the
schema/queries behind the relational version, and a results page with the
numbers I re-checked while putting this repository together.

## Analytical Question

How does medication utilisation — measured as the average number of distinct
medications per patient — differ between synthetic patients with a chronic
condition and those without, and does that result reproduce consistently
across a relational (SQL), document-oriented (MongoDB), and distributed
(PySpark) implementation of the same analysis?

## Dataset

**Australian synthetic healthcare data with Synthea**, published by CSIRO on
the [Data Access Portal](https://data.csiro.au), authored by Ibrahima Diouf
(DOI: [10.25919/efcw-bm49](https://doi.org/10.25919/efcw-bm49)), licensed
CC BY 4.0. The dataset contains **synthetic healthcare records and does not
represent real patients** — it was generated with an Australianised version
of Synthea from population-level demographic and disease statistics, and
contains 117,258 synthetic Queensland patients in total.

This project uses 8 of the official collection's 17 CSV tables: `patients`,
`encounters`, `conditions`, `medications`, `procedures`, `immunizations`,
`organizations`, `providers`. The full CSIRO collection also ships per-patient
FHIR JSON and a separate 300,000-patient bulk FHIR export — neither is used
here. See [`data/README.md`](data/README.md) for the complete table list,
including which official tables are *not* used, and how to obtain the data.
**This repository does not contain the full CSIRO collection or any raw
patient-level data.**

## Data Integrity

I checked the 8 CSV files I used against CSIRO's official
`collection_import_sha256sum.txt` SHA-256 manifest, and all 8 hashes matched.
I never downloaded the other 9 tables or the FHIR datasets, so they aren't
covered by that check.

## Working Subset

All analysis runs against a reproducible 5,000-patient random sample (seed
42) of the 117,258 available patients, generated by
[`scripts/subset_synthea_data.py`](scripts/subset_synthea_data.py). The
sampled patient ID set is used to filter `encounters`, `conditions`,
`medications`, `procedures`, and `immunizations`; `organizations` and
`providers` are copied unfiltered since they're small reference tables. See
[`data/README.md`](data/README.md) for exact commands.

## Analytical Approaches

### SQL / SQLite

[`sql/schema.sql`](sql/schema.sql) defines the relational schema for the 8
tables. [`sql/analysis_queries.sql`](sql/analysis_queries.sql) implements the
chronic-vs-non-chronic medication comparison, the most-prescribed medication
per condition, and cost per condition — joining `conditions` to `medications`
on `(PATIENT, ENCOUNTER)` so a condition from one visit is never paired with
a medication from a different visit.

### MongoDB

[`mongodb/load_synthea_to_mongo.py`](mongodb/load_synthea_to_mongo.py) embeds
each patient's encounters directly in their document, and each encounter's
conditions and medications directly in that encounter — a deliberate
denormalisation, since "everything from this visit" is the unit most queries
need. Organisations and providers are referenced by ID rather than embedded,
since the same organisation/provider appears across thousands of patients.
[`mongodb/mongo_queries.py`](mongodb/mongo_queries.py) reproduces the same
comparison using `$unwind` and `$group` aggregation pipeline stages instead
of SQL joins.

### PySpark

[`pyspark/pyspark_analysis.py`](pyspark/pyspark_analysis.py) re-implements
the same comparison as Spark DataFrame transformations: filtering conditions
by keyword, joining to medications on `(PATIENT, ENCOUNTER)`, and grouping to
compute per-patient distinct medication counts.

## Results

The numbers below came from running `sql/analysis_queries.sql` and
`pyspark/pyspark_analysis.py` against the same subset. Full detail, including
how I reconciled the two denominator conventions, is in
[`results/verified_results.md`](results/verified_results.md).

| Analysis | SQL (all patients) | SQL (≥1 medication) | PySpark |
|---|---:|---:|---:|
| Chronic-group avg. distinct medications | 6.20 (n=2,717) | 6.3 (n=2,675) | 6.3 (n=2,675) |
| Non-chronic avg. distinct medications | 3.75 (n=2,283) | 4.11 (n=2,088) | 4.11 (n=2,088) |
| Relative difference | +65% | +53% | +53% |

SQL and PySpark agree **exactly** once both use the same denominator
(patients with at least one medication on record). The "all patients"
variant is lower because it counts patients with zero medications as 0
rather than excluding them — both conventions are valid, and both are kept
in `sql/analysis_queries.sql` (Q1 and Q1b) rather than picking one silently.

I didn't re-run the MongoDB query live for this comparison — see
[`results/verified_results.md`](results/verified_results.md) for why, and for
a note on a possible third denominator convention in its aggregation
pipeline that I haven't confirmed against real output yet. That's a gap in
what I've checked, not a claim that MongoDB disagrees.

These are descriptive statistics over synthetic data, not a clinical or
causal finding.

## Validation and Analytical Corrections

Cross-checking the three implementations against each other caught two
mistakes while I was building this out, both still visible in the code's
comments and both fixed in the versions here:

**Encounter-aware joins.** An earlier version joined `conditions` to
`medications` on `PATIENT` alone. Since a patient can have many encounters,
this silently paired a chronic condition diagnosed in one visit with a
medication prescribed in a completely unrelated visit, inflating the
apparent condition–medication association. The corrected join in
`sql/analysis_queries.sql` and `pyspark/pyspark_analysis.py` matches on
`(PATIENT, ENCOUNTER)`, so only medications from the same visit as the
condition are counted.

**`count` vs `countDistinct`.** An early PySpark attempt at "average
medications per patient" used `count`, which counts every prescription row —
including refills of the same medication — producing an implausible average
of roughly 114 medications per patient. The corrected version uses
`countDistinct` on medication description, counting how many *different*
medications a patient has been prescribed rather than how many times they
filled any prescription.

I'm leaving both of these in the writeup rather than quietly fixing them and
moving on — catching them is exactly what running the same analysis three
different ways was supposed to do.

## Why Multiple Paradigms?

- **SQL** gives structured relational analysis with explicit joins and
  straightforward aggregation — the natural fit for a fixed, well-defined
  schema.
- **MongoDB** models each patient's care as one denormalised document, so
  queries about "this patient's history" don't need a join at all, at the
  cost of embedding logic (like the chronic-condition flag) into the
  document-build step rather than the query.
- **PySpark** expresses the identical transformations as distributed
  DataFrame operations, which is the paradigm that would scale past a single
  machine if applied to the full 117,258-patient population.

No performance or scalability comparison was benchmarked between the three;
none is claimed here.

## Reproducibility

```bash
git clone https://github.com/waleedmaqsood20/synthea-multiparadigm-healthcare-analysis.git
cd synthea-multiparadigm-healthcare-analysis

python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate

pip install -r requirements.txt
```

**1. Get the data.** Follow [`data/README.md`](data/README.md) to obtain the
8 required CSVs from the CSIRO Data Access Portal and place them in
`data/raw/`.

**2. Build the subset.**
```bash
python scripts/subset_synthea_data.py
```

**3. SQL.** Build a local SQLite database from `data/subset/*.csv` using
`sql/schema.sql`, then run the queries in `sql/analysis_queries.sql` against
it (e.g. via the `sqlite3` CLI or any SQLite client).

**4. MongoDB.**
```bash
cp .env.example .env
# edit .env and set MONGODB_URI to your own connection string
python mongodb/load_synthea_to_mongo.py
python mongodb/mongo_queries.py
```
Never commit `.env` — it is git-ignored, and `.env.example` only ever
contains a placeholder.

**5. PySpark.** Requires a JDK (17+) with `JAVA_HOME` set in your shell —
PySpark needs a JVM to run. Install one (e.g. Microsoft Build of OpenJDK,
Temurin), set `JAVA_HOME` to its install path, then:
```bash
python pyspark/pyspark_analysis.py
```
The script checks for `JAVA_HOME` and exits with an explanatory message if
it isn't set, rather than hardcoding a path.

## Limitations

- The data are synthetic; results describe a Synthea-generated population,
  not real patients, and are not clinical evidence.
- All analysis uses a 5,000-patient subset of the 117,258 available, not the
  full collection.
- Only 8 of the 17 official CSV tables were used; the per-patient FHIR and
  300k-patient bulk FHIR exports were not used at all.
- "Chronic condition" is a project-specific definition (substring match on
  four keywords in the condition description), not a clinical classification.
- I haven't re-verified the MongoDB numbers against a live run recently (see
  Results) — treat those specifically as unconfirmed until I do.
- No performance/scalability benchmarking was done between SQL, MongoDB, and
  PySpark; none should be inferred from this repository.
- Local SQLite/MongoDB/PySpark setups may behave differently at larger scale
  than the 5,000-patient subset used here.
